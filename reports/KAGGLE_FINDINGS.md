SHA256 исходников: `6778485712c29058303916a56480400352e6c38de6e4e29785026a6bc3157362`.
SHA256 ZIP: `0c6f99d1abd2a77fdda3c7ea3ca72e5ad43eb2cbf78a0ad819de12be81090776`.

## Контроль с бюджетом 300 секунд

Дополнительно выполнена пара запусков на California Housing с тем же seed и
разбиением, по 300 секунд на каждый режим. Оба получили RMSE **45 234,99**.
Без Qwen потребовалось 87,4 секунды, с Qwen — 127,6 секунды. Оба API-запроса
снова завершились `TimeoutError`, обученных Qwen-кандидатов нет; итоговые CSV
совпали побайтно.

Следовательно, причина не ограничивается коротким 90-секундным бюджетом:
тайм-ауты сохраняются при текущем потолке ожидания API в 20 секунд. Логи не
различают тайм-аут соединения и ожидания ответа модели. По ним нельзя установить,
недоступен ли прокси или модель отвечает медленнее. Это локальный результат,
его нельзя автоматически приписывать окружению Boosters.

Подробности: [kaggle-research-300.json](kaggle-research-300.json),
[таблица](kaggle-research-300.md). Выигрыш RMSE относительно 90-секундного поиска
составил около 0,46%; увеличение бюджета само по себе не дало большого скачка.
При этом оба поиска закончились раньше своих предельных бюджетов.

## Что уже видно

**Qwen пока не дал ни одного обученного эксперимента в короткой серии.** Все
шесть API-запросов завершились `TimeoutError`, `qwen_fits = 0`. Предсказания
совпали с вариантом без Qwen. Это проверка запасного поиска при недоступном
исследователе; качество сгенерированных признаков этим замером не оценено.
В текущем runtime время ожидания API равно `min(20, remaining * 0.1)` с нижним
ограничением в одну секунду. При коротком запуске оно обычно меньше 10 секунд.

**Фиксированная модель уже близка к полному поиску.** LightGBM занял 7,6–18,3
секунды на набор, поиск без Qwen — 31,2–76,3 секунды. Его преимущество по качеству
пока небольшое. В режиме 90 секунд агент начинает с 150 итераций бустинга,
фиксированный ориентир — с 500; при штатных 900 секундах портфель начинает с
1800. Поэтому эту серию нельзя выдавать за оценку конкурсного запуска на
штатном бюджете.

## Что улучшать следующим

1. **Обеспечить измеримую работу Qwen.** До сравнения качества требовать хотя бы
   один успешный ответ и один обученный Qwen-кандидат. Записывать задержку и
   отдельно причины тайм-аутов соединения и чтения ответа. Проверить доступность
   прокси. Отдельно проверить короткий JSON-ответ с
   несколькими гипотезами и больший ограниченный срок ожидания, сохраняя резерв
   на обучение и refit. Каждый вариант сравнивать при том же общем бюджете.
2. **Проверить распределение времени.** Сравнить портфель из LightGBM/XGBoost с
   полным портфелем. Освободившееся время направить на локальный поиск вокруг
   удачной модели и более содержательные признаки. Жёсткие ограничения в 30
   поисковых экспериментов и 10 попыток без улучшения иногда заканчивают работу
   раньше срока; дополнительные попытки нужны только при новых гипотезах.
3. **Измерить пользу смысловых признаков.** Просить Qwen выбирать операции по
   словарю колонок, ошибкам и важности модели: отношения величин, плотности,
   взаимодействия категорий, агрегаты по группам. Менять признаки при неизменных
   модели, seed и разбиении; оставлять выигрыш только после абляции и контроля.
   Отдельная проверяемая гипотеза для категорий — сглаженный target encoding
   с cross-fitting внутри обучающей части. Названия Kaggle-наборов и готовые
   ответы не должны появляться в ветвлениях агента.
4. **Точнее оптимизировать метрику.** Для бинарного Macro F1 проверить подбор
   порога, для нескольких классов — ограниченный поиск поправок вероятностей.
   В runtime уже есть небольшая сетка поправок по частотам классов: новый
   вариант должен обойти её на независимом контроле. Для регрессии сравнивать
   преобразование цели и параметры бустинга по исходной метрике.
5. **Подтвердить улучшение перед сабмитом.** Сначала быстрые development-прогоны,
   затем 300–900 секунд и несколько seeds для выбранных изменений. Финальный
   резерв открывать после выбора версии. Повторные решения по его оценке
   постепенно превратят его в ещё одну обучающую выборку для разработчика.

Эти пункты — приоритеты экспериментов, а не обещание роста конкурсного балла.
Новые стратегии в runtime этим коммитом не добавлялись; готовый конкурсный ZIP
остался прежним.

## Проверки стенда

Полный набор: **225 тестов прошли, ошибок и пропусков нет**;
[JUnit-отчёт](kaggle-tests.xml). Среди них проверены разбиение дубликатов,
