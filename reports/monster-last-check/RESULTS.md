# Последняя проверка monster.zip

Проверен неизменённый архив `30e053296722de373df8b82cef26a976df8220a696aa1a6cd36cb173e2b61189`.

- 11 адресных unit-тестов: унаследованные лимиты памяти, ограничение потоков контроллера, явный отказ при полном отсутствии fit, SIGKILL/watchdog и гонки завершения процессов.
- Точный flat CLI в Linux, 8 CPU / 6 GiB / без сети: по шесть успешных семейств (linear, LightGBM, CatBoost, HistGB, ExtraTrees, XGBoost) в регрессии и классификации. Эти две пробы остановлены диагностическим SIGTERM после начального портфеля.
- Тот же CLI при одновременно pids.max=30 и унаследованном hard/soft RLIMIT_AS=8 GiB: по две успешных модели (linear, LightGBM) на каждой задаче; лимит не повышается. Пробы также остановлены диагностически.
- Всего в Linux 16 успешных fit, 0 ошибок workers, четыре валидных обученных CSV. Это проверка работоспособности, а не сравнение ML-качества.
- Отдельно выполнен flat bootstrap с development hook 90 с / 2 поисковых попытки: полный refit, валидные IDs/schema/конечные значения, отклонение испорченного checksum.
- Архив и все прежние ZIP не изменены. На платформу ничего не отправлялось.

Стенд сначала отклонил неподдерживаемое Docker `--ulimit as` до запуска агента. Лимит корректно установлен через `resource.setrlimit` с последующим exec неизменённого entrypoint; предыдущие успешные обычные пробы не повторялись. Это исправление тестового стенда, runtime не менялся.

В проверках нет повторения локально воспроизведённых причин полного отказа workers. Исходное серверное исключение неизвестно. Полный образ организаторов, 10500-секундный запуск и скрытые задачи не проверялись. Ненулевой балл не гарантирован: возможны другие ограничения среды или непревосхождение скрытого baseline.
